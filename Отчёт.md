# Отчёт: платформа вакансий и резюме

## 1. Доменная область

Веб-платформа для поиска работы, которая связывает работодателей и соискателей.

- **Соискатель** регистрируется, подтверждает email, заполняет резюме (с фотографиями), просматривает вакансии и откликается на них.
- **Сотрудник компании (работодатель)** регистрирует компанию, публикует и редактирует вакансии, просматривает отклики.
- **Администратор** модерирует компании (подтверждает регистрацию), управляет вакансиями и компаниями.

При регистрации, смене email, восстановлении пароля и новом отклике пользователю приходит email-уведомление.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Frontend | Next.js 15, React 19, TypeScript, Tailwind CSS, axios |
| Backend | Java 17, Spring Boot 3.4 (Web, Security, Data JPA, Actuator), JWT (jjwt) |
| СУБД | PostgreSQL 16 (две БД: `AuthDb` и `CompVacDb`) |
| Миграции | Liquibase |
| Брокер сообщений | Apache Kafka 3.8 (режим KRaft) |
| Кэш / служебные данные | Redis 7 (blacklist JWT-токенов после logout) |
| Файловое хранилище | Yandex Object Storage (S3-совместимое) для изображений резюме |
| Входная точка | Nginx (reverse proxy и балансировка между репликами) |
| Окружение | Docker, Docker Compose |
| Логи (опционально) | Graylog + Elasticsearch + MongoDB |

Взаимодействие клиента с бэкендом идёт через HTTP/1.1 REST.

### Архитектура

```
Браузер ──► nginx :80 ──┬── /            ──► frontend (Next.js)
                        ├── /api/auth/*  ──► auth-service ×N ──► PostgreSQL AuthDb, Redis, S3
                        ├── /api/user/*  ──┘
                        └── /api/comp-vac/* ► company-vacancy-service ×N ──► PostgreSQL CompVacDb
auth-service, company-vacancy-service ──(события)──► Kafka ──► notification-service ──► SMTP
```

| Сервис | Ответственность |
|---|---|
| `auth-service` | регистрация, вход, JWT, профиль, смена email/пароля, CRUD резюме и изображений резюме |
| `company-vacancy-service` | CRUD компаний, вакансий, откликов; модерация компаний |
| `notification-service` | читает события из Kafka и отправляет письма |
| `frontend` | пользовательский интерфейс |

## 3. Основные сущности

**БД `AuthDb` (auth-service)**

| Сущность | Поля | Связи |
|---|---|---|
| `Role` (роль) | `role_id`, `title` | 1 — Администратор, 2 — Пользователь, 3 — Сотрудник |
| `User` (пользователь) | `user_id`, `login` (email, уникальный), `password` (bcrypt), `pending_login`, `enabled` | N:1 → `Role`; 1:1 → `Resume` |
| `Resume` (резюме) | `resume_id` (= `user_id`), `full_name`, `gender`, `birthday`, `education`, `place_education`, `skills`, `phone`, `contact`, `description`, `date` | 1:1 → `User`; 1:N → `ResumeImage` |
| `ResumeImage` (изображение резюме) | `resume_image_id`, `url` (ключ объекта в S3) | N:1 → `Resume` |

**БД `CompVacDb` (company-vacancy-service)**

| Сущность | Поля | Связи |
|---|---|---|
| `Company` (компания) | `company_id`, `name`, `inn`, `kpp`, `ogrn`, `address`, `director`, `date_reg`, `is_accepted`, `user_name` (владелец) | 1:N → `Vacancy` |
| `Vacancy` (вакансия) | `vacancy_id`, `name`, `title`, `description`, `contact`, `experience`, `format`, `address`, `schedule`, `hours`, `is_educated`, `is_hidden`, `date` | N:1 → `Company`; 1:N → `Response` |
| `Response` (отклик) | `response_id`, `user_name` (соискатель), `is_viewed`, `date` | N:1 → `Vacancy` (`ON DELETE SET NULL`) |

### CRUD-операции (REST)

| Сущность | Create | Read | Update | Delete |
|---|---|---|---|---|
| Резюме | `POST /api/user/resume` | `GET /api/user/resume`, `GET /api/user/resume/{id}` | `PUT /api/user/resume/{id}` | `DELETE /api/user/resume/{id}` |
| Изображение резюме | `POST /api/user/{resumeId}/image` | `GET /api/user/{resumeId}/images/content` | — | `DELETE /api/user/resume-image/{id}/content` |
| Компания | `POST /api/comp-vac/company` | `GET /api/comp-vac/company`, `GET /api/comp-vac/company/{id}` | `PUT /api/comp-vac/company/{id}` | `DELETE /api/comp-vac/company/{id}` |
| Вакансия | `POST /api/comp-vac/vacancy` | `GET /api/comp-vac/vacancy`, `GET /api/comp-vac/vacancy/{id}` | `PUT /api/comp-vac/vacancy/{id}` | `DELETE /api/comp-vac/vacancy/{id}` |
| Отклик | `POST /api/comp-vac/vacancy/{id}/response` | `GET /api/comp-vac/responses`, `GET /api/comp-vac/responses/{id}` | — | при удалении вакансии |
| Пользователь | `POST /api/auth/register` | `GET /api/auth/profile` | `PUT /api/auth/profile`, `PUT /api/auth/profile/change-login` | — |

## 4. Соответствие методологии «12 факторов»

### I. Кодовая база (Codebase)
**Соответствует.** Весь код лежит в одном git-репозитории. Каждый сервис (`auth-service`, `company-vacancy-service`, `notification-service`, `frontend`) — отдельно собираемое и разворачиваемое приложение со своим `Dockerfile` и манифестом зависимостей. Это монорепозиторий, но общего кода между сервисами на уровне сборки нет, поэтому каждый собирается из одной кодовой базы независимо. Любое окружение (локальное, CI, «прод») разворачивается из одного и того же репозитория, отличается только конфигурация. Артефакты сборки, логи, настройки IDE и `.env` исключены через `.gitignore`.

### II. Зависимости (Dependencies)
**Соответствует.** Зависимости объявлены явно: Maven (`pom.xml`) для Java-сервисов и npm (`package.json` + `package-lock.json`) для фронтенда. Сборка не полагается на системные пакеты: JDK, Maven и Node.js приходят из базовых образов фиксированных версий (`maven:3.9-eclipse-temurin-17`, `node:20-alpine`). Фронтенд ставит зависимости через `npm ci` строго по lock-файлу.

### III. Конфигурация (Config)
**Соответствует.** Всё, что меняется между окружениями, читается из переменных окружения:
- в `application.properties` используются только подстановки `${DB_URL}`, `${DB_PASSWORD}`, `${JWT_SECRET}`, `${KAFKA_BOOTSTRAP_SERVERS}`, `${CORS_ALLOWED_ORIGINS}`, `${MAIL_*}`, `${YC_*}` и т.д.;
- у секретов нет значений по умолчанию: без них сервис не стартует (fail fast);
- захардкоженные `http://localhost` вынесены во фронтенде в `NEXT_PUBLIC_API_URL`, в письмах — в `FRONTEND_URL`, в CORS — в `CORS_ALLOWED_ORIGINS`;
- учётная запись администратора задаётся через `ADMIN_LOGIN` / `ADMIN_PASSWORD`, а не в коде;
- шаблон конфигурации `.env.example` лежит в репозитории, файл `.env` с реальными значениями — нет.

Проверка «можно ли сейчас открыть код без утечки секретов» выполняется: в репозитории нет паролей и ключей.

### IV. Сторонние службы (Backing Services)
**Соответствует.** PostgreSQL, Redis, Kafka, SMTP-сервер, S3-хранилище и Graylog — подключаемые ресурсы, адреса и учётные данные которых задаются через конфигурацию. Например, чтобы перейти с локального Postgres на управляемый облачный, достаточно поменять `DB_URL` / `DB_PASSWORD`. Для замены SMTP или S3 тоже меняются только переменные, код остаётся прежним.

### V. Сборка, релиз, выполнение (Build, release, run)
**Соответствует.** Этапы разделены:
- **сборка**: `docker compose build` выполняет многоэтапный (multi-stage) `Dockerfile`; исходники компилируются внутри образа (`mvn package`, `next build`), итоговый образ содержит только JRE/Node и артефакт;
- **релиз**: образ с тегом `APP_VERSION` плюс конфигурация из `.env`;
- **выполнение**: `docker compose up` запускает готовые образы, код во время выполнения не меняется.

Устаревший скрипт `build.bat`, собиравший JAR вне контейнера, удалён.

### VI. Процессы (Processes)
**Соответствует.** Сервисы не хранят состояние между запросами:
- аутентификация через JWT, сессий в памяти нет; отозванные токены (logout) хранятся в Redis;
- данные хранятся в PostgreSQL, изображения резюме — в S3, а не в локальной файловой системе контейнера;
- поэтому любой запрос может обработать любая реплика, что и происходит за nginx.

### VII. Привязка портов (Port binding)
**Соответствует.** Каждый сервис — самодостаточное приложение со встроенным веб-сервером (Tomcat в Spring Boot, Node.js-сервер Next.js standalone), он сам слушает порт из переменной `PORT`. Внешний веб-сервер для запуска не нужен. Nginx не исполняет приложение, а только маршрутизирует трафик между сервисами.

### VIII. Параллелизм (Concurrency)
**Соответствует.** Масштабирование горизонтальное, запуском нескольких процессов. `auth-service` и `company-vacancy-service` по умолчанию работают в двух репликах (`AUTH_REPLICAS`, `COMPVAC_REPLICAS` или `docker compose up --scale ...`), nginx распределяет запросы между ними (round-robin). Типы процессов разделены: веб-процессы обрабатывают HTTP, а `notification-service` — фоновый обработчик очереди Kafka. Его тоже можно масштабировать: потребители одной consumer group делят партиции.

### IX. Утилизируемость (Disposability)
**Соответствует.**
- Быстрый запуск: процессы стартуют за несколько секунд, образы содержат только JRE и jar.
- Корректное завершение: включено `server.shutdown=graceful`. По SIGTERM сервис перестаёт принимать новые запросы и дожидается текущих (`SHUTDOWN_TIMEOUT`, по умолчанию 20 с, у Compose `stop_grace_period: 30s`). JVM запускается в exec-форме `ENTRYPOINT` и получает сигнал напрямую.
- Готовность: эндпоинт `/actuator/health/readiness` используется в `HEALTHCHECK` образа, nginx стартует только после того, как бэкенд стал healthy.
- Устойчивость: `restart: unless-stopped`. Kafka хранит события до их обработки, поэтому перезапуск `notification-service` не теряет уведомления.

### X. Паритет разработки и продакшена (Dev/prod parity)
**Соответствует.** Локально используются те же сторонние службы, что и в рабочем окружении: PostgreSQL, Redis и Kafka, без H2 или in-memory заглушек. Версии образов зафиксированы (`postgres:16.4-alpine`, `redis:7.4-alpine`, `apache/kafka:3.8.0`, `nginx:1.27-alpine`) вместо `latest`. Данные БД хранятся в именованных volumes. Тесты в CI тоже идут на настоящих PostgreSQL и Kafka через Testcontainers. Окружение поднимается одной командой, поэтому разрыв между разработкой и развёртыванием минимален.

### XI. Журналирование (Logs)
**Соответствует.** Приложения не управляют файлами логов, а пишут поток событий в stdout (`ConsoleAppender` в `logback-spring.xml`, nginx пишет в `/dev/stdout` и `/dev/stderr`). Сбор и маршрутизация — задача окружения: `docker compose logs`, а при подключении `docker-compose.observability.yml` логи дополнительно уходят в Graylog. Отправка в Graylog включается профилем `graylog` через переменную окружения, адрес задаётся в `GRAYLOG_HOST`, в коде не захардкожен. Файлы логов из репозитория удалены.

### XII. Задачи администрирования (Admin processes)
**Соответствует.** Административные задачи выполняются как код из той же кодовой базы, в том же релизе и окружении, что и приложение:
- **миграции схемы БД** — версионированные changeset-ы Liquibase (`src/main/resources/db/changelog`) вместо `ddl-auto=update`. Hibernate работает в режиме `validate` и только проверяет соответствие схемы. Миграции применяются при старте релиза, а таблица блокировок `DATABASECHANGELOGLOCK` не даёт двум репликам применить их одновременно. Автозапуск можно отключить (`LIQUIBASE_ENABLED=false`);
- **начальные данные**: справочник ролей заполняется миграцией, первичный администратор создаётся из переменных окружения;
- **разовые задачи** выполняются в том же окружении, например `docker compose exec auth-db psql ...` или запуск контейнера сервиса через `docker compose run`.

